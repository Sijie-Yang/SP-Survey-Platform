# 第一轮：版本管理、完整读取与提交恢复

## 上线顺序（本轮需要 Supabase 迁移）

现有数据库需先包含 `agent_mcp_platform.sql` 和 `survey_public_rpcs.sql` 的基础结构。在 Supabase SQL Editor 依次执行：

1. `supabase/response_retry.sql`：新增支持幂等重试的答卷提交函数。
2. `supabase/research_releases.sql`：新增版本管理开关、发布媒体清单、原子发布/恢复函数，并更新参与者读取函数。
3. 部署前端和 Worker/Express 代码。不要先部署新前端再补提交函数，否则新提交会进入重试状态。

用户已确认在 Supabase 执行两份迁移。本地管理界面已成功读取实际数据库的版本字段与历史列表，没有缺列或缺函数错误；测试项目仍保持未启用版本管理。尚未推送或部署，也未对真实研究执行发布、恢复或测试答卷提交。SQL 事务行为已在本地临时 PostgreSQL 环境验证；匿名线上提交仍需上线验收。

脚本支持重复执行。后续不要单独重跑旧 `survey_public_rpcs.sql` 来覆盖新版参与者读取函数；若更新基础脚本，最后重跑 `research_releases.sql`。

## 产品入口与行为

管理员 → 项目 → Step 3 / Share Survey → Survey versions（问卷版本管理）。

- 现有项目默认保留“保存即生效”，避免迁移突然改变正在收集的项目。
- 点击“启用版本管理并发布”，检查变化、填写说明并确认后，保存只更新草稿；正式分享链接读取最后发布的题目和媒体清单。
- 已登录的项目所有者通过参与者链接也读取正式版；编辑器预览继续读取草稿。
- 发布前检查配置与媒体分配；正式版不再临时使用平台预览媒体库作为空媒体池的后备。
- 按每页 20 个版本加载历史，展示新增/修改/删除的题目、变化字段和媒体数量。
- 恢复旧版会新增版本，同时替换草稿与媒体分类；不会删除历史版本或答卷。
- 发布/恢复在一个事务内执行，使用草稿时间戳校验，避免覆盖其他标签页或 Agent 的新修改。MCP 发布与恢复同样需要 `expectedDraftUpdatedAt`。
- 老快照没有媒体清单，明确标为仅可查看，不能假装完整恢复。恢复清单也不会重新创建已物理删除的文件。
- 本轮版本管理支持 Supabase 平台模式；纯文件自托管模式继续现有流程，界面会说明不可用。

## 结果完整性

管理员、项目所有者与 Agent 读取答卷均持续分页到空页，不再用“少于 1000 条”推断结束。采用时间戳和答卷 ID 的游标；采集新答卷或删除已读行不会使后续页按偏移错位。无日期记录单独稳定排序。遇到读取失败、重复页或超过 500,000 行安全上限时明确报错，不展示部分数据为完整分析。

这是分页完整性修复，不是跨所有页面的数据库事务快照。正在修改/删除尚未读取的答卷可能影响本次结果；正式归档应在停止收集和数据清理后导出，并保留筛选记录。

## 断网与提交恢复

- 提交请求发出前先保存完整待提交内容及完成码。
- 30 秒没有收到确认会进入可重试状态，原请求晚到也不会使用新完成码。
- 刷新后优先恢复待提交答卷，不需要重新加载问卷媒体，也不会因研究此时达到名额而挡住原答卷重试。
- 匿名提交函数在数据库事务里锁定项目/参与者/完成码，重复发送同一答案返回既有回执；相同码但答案不同则拒绝。
- 浏览器无法保存恢复副本时明确提示保持页面打开；提交失败页提供答卷 JSON 下载备份。
- 只有服务端确认成功后才清除草稿和待提交副本。
